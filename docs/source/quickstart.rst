.. _quickstart:

Quick start guide
-----------------

First time set-up
`````````````````

.. note::

    This section assumes that **tomato** has been successfully :ref:`installed<installation>`.

The easiest way to set-up **tomato** for its first run is to run ``tomato init``:

.. code-block::
   :linenos:
   :emphasize-lines: 2

    kraus@dorje:~$ tomato init
    Success: wrote default settings into /home/kraus/.config/tomato/3.0rc6/settings.toml

This will create a |setfile|_ and a |devfile|_ in **tomato's** *appdir* folder. By default, the *appdir* path is:

- ``$env:localappdata\dgbowl\tomato\<version>`` on Windows,
- ``$HOME/.config/tomato/<version>`` on Linux.

.. tip::

    In the above example, the *appdir* is ``/home/kraus/.config/tomato/3.0rc6/``, as highlighted on line 2. A custom *appdir* can be specified using the ``--appdir`` argument to **tomato** via ``tomato init`` and ``tomato start``.

.. note::

    Any existing |setfile|_ and/or |devfile|_ within the *appdir* will **not** be overwritten when ``tomato init`` is called. If you have corrupted either of the two configuration files, make a backup, delete the files, and run ``tomato init`` again.

You can now start **tomato** using ``tomato start``:

.. code-block::

    kraus@dorje:~$ tomato start
    Success: tomato running on port 1234

.. _concepts:

Key **tomato** concepts
```````````````````````
Before you start configuring your **tomato** instance, you should be familiar with the following concepts, that are used in **tomato** and in this documentation:

- *devices*, which represent separately addressable (and optionally multichannel) instruments in the lab,
- *components*, which represent the individual channels or components of each *device*, describing the role of this *component* and its associated capabilities,
- *pipelines*, which represent the real world organisation of device *components* into independent experimental set-ups, containing *components* from one or more *device*,
- *jobs*, which are processes that carry out a set of *tasks* (set of experimental instructions, i.e. a *payload*) on a *pipeline* by instructing its *components* to perform individual *tasks*, and
- *drivers*, which are processes talking to the hardware, with each *driver* managing all defined *devices* of a certain driver type, including all their *components*.

Consider the below diagram:

.. mermaid::
    :caption: Diagram of **tomato** concepts.

    flowchart LR

      c1 --- drv1[driver 123]
      c2 --- drv1
      c3 --- drv1

      a100 --- drv2[driver abc]
      b100 --- drv2

      subgraph d1[device 1]
          ip1[address: 192.168.1.1]
          c1[channel 1]
          c2[channel 2]
          c3[channel 3]
      end

      subgraph a[device a]
          com1[address: COM1]
          a100[channel 100]
      end

      subgraph b[device b]
          com2[address: COM2]
          b100[channel 100]
      end

      subgraph pipelines
          pip1
          pip2
          pip3
      end

      pipelines:::config

      subgraph drivers
          drv1
          drv2
      end

      subgraph devices
          d1:::config
          a:::config
          b:::config
      end

      devices:::config

      subgraph jobs
          j1
          j2
      end

      j1[complex] --- |payload:<br/>0-9<br/>a-z| pip1
      j2[simple] --- |payload:<br/>0-9| pip3

      pip1[pipeline a1] -.-> c1
      pip1[pipeline a1] -.-> a100

      pip2[pipeline b2] -.-> c2
      pip2[pipeline b2] -.-> b100

      pip3[pipeline 3] -.-> c3

      classDef config fill:#fff,stroke:#5c5

Here, three devices are defined in the |devfile|_ (``device 1``, ``device a``, and ``device b``). Three pipelines (``pipeline a1``, ``pipeline b2``, and ``pipeline 3``) as well as the links to the components are also defined in the |devfile|_. Based on this information, the ``tomato-daemon`` process knows it needs to launch two drivers, one for ``device 1``, and a second one for ``device a`` and ``device b``.

Jobs are also managed in separate processes. They are matched against pipelines based on the contents of their |payfile|_. In the above example, the **simple** job, requiring ``0-9`` in its payload, could match against any of the three configured pipelines, as each pipeline contains a "numerical" component from ``device 1``. The **complex** job, requiring both ``0-9`` as well as ``a-z`` in its payload, can only be matched against ``pipeline a1`` or ``pipeline b2``.

.. _settings-file:

Settings file
`````````````
The *settings file* contains the basic information required to start the ``tomato-daemon``. The file path is hard-coded to be a ``settings.toml`` file, which has to be located in the *appdir*. The default file generated by ``tomato init`` looks similar to the below example:

.. code-block:: toml
   :linenos:

    datadir = '/home/kraus/.local/share/tomato/1.0a1'
    logdir = '/home/kraus/.cache/tomato/1.0a1/log'

    [jobs]
    storage = '/home/kraus/.local/share/tomato/1.0a1/Jobs'
    dbpath = '/home/kraus/.local/share/tomato/1.0a1/Jobs/dbpath.sqlite'

    [devices]
    config = '/home/kraus/.config/tomato/1.0a1/devices.yml'

    [repositories]
    default.endpoint = 'https://example.endpoint/uri-here'
    default.api_key = 'your-api-key-here'

    [drivers]
    example_counter.idle_measurement_interval = 1


In addition to the *appdir*, a second path, *datadir*, is used to specify the location of the data created by **tomato**. The default *datadir* is:

- ``$env:localappdata\dgbowl\tomato\<version>`` on Windows,
- ``$HOME/.local/share/tomato/<version>`` on Linux.

Finally, another path, *logdir*, is used to specify where logs for **tomato** are placed. By default, *logdir* is:

- ``$env:localappdata\dgbowl\tomato\<version>`` on Windows,
- ``$HOME/.cache/tomato/<version>/log`` on Linux.

**jobs** section
****************

Section for configuring behaviour of **tomato** jobs. The following entries can be specified:

- ``jobs.storage`` which is the directory where the data of **tomato** jobs will be stored
- ``jobs.dbpath`` which is the location of the ``sqlite3`` database used to track jobs

**devices** section
*******************

Section for configuring **tomato** devices. The following entries can be specified:

- ``devices.config`` which points to a ``yaml``-formatted |devfile|_, defining the hardware configuration of the devices managed by **tomato**

**repositories** section
************************

.. note::
    The upload to repositories functionality is not yet fully implemented.

Section for settings related to the upload of completed payloads to pre-configured repositories using the RO-crate mechanism. By default, all payloads will attempt to submit to the ``default`` repository, which can be configured as follows:

- ``repositories.default.endpoint`` should be the API endpoint of the repository where the RO-crates should be sent
- ``repositories.default.api_key`` should contain any API key / token necessary for authenticating the upload

More than one repository can be specified using a separate sub-section. If a ``default`` repository is not specified, RO-crate objects will **not** be created and data from completed payloads will **not** be uploaded.

**drivers** section
*******************

Additional, driver-specific settings may be provided in this section. Each driver should be configured separately in its own sub-section. The following entries can be specified for all drivers:

- ``drivers.<driver_name>.idle_measurement_interval`` for configuring the interval between measurements performed when any registered component is idle, in seconds,
- ``drivers.<driver_name>.lpp_timeout`` for configuring the timeout for communication between **tomato** and the driver process, in seconds.

Further driver-specific settings, such as ``dllpath`` or ``calibration``, can be specified here. All of these driver-specific settings are passed to each driver. For more details, see the `tomato driver development <develop_driver.html>`_ documentation.

.. _devices-file:

Devices file
````````````
This ``yaml``-formatted file contains information about each device, corresponding to an individual piece of hardware managed by **tomato**, as well as information about the organisation of the individually-addressable components of those devices into pipelines.

When the *devices file* is not present, the default file shipped with **tomato** will be used instead. The sections of this default *devices file* are discussed below:

**devices** section
*******************
The ``devices`` section of the default |devfile|_ is shown below:

.. code-block:: yaml
   :linenos:

    devices:
      - name: dev-counter
        driver: "example_counter"
        address: "example-addr"
        channels: ["1"]
        pollrate: 1

Here, we define a single device using the :mod:`tomato-example-counter` driver. The definition includes the ``address`` of the device (of type :class:`str`) as well as an enumeration of individually-addressable ``channels`` the device has (of type :class:`list[str]`). The ``address`` and each of the ``channels`` will then be used to define the components on this device.

.. note::

    What needs to be specified as device ``address``/``channels``, or if anything has to be specified at all, depends on each of the **tomato** drivers. Please refer to the **tomato** driver library in the sidebar.


**pipelines** section
*********************
The default ``pipelines`` section looks as follows:

.. code-block:: yaml
    :linenos:
    :emphasize-lines: 5

    pipelines:
      - name: pip-counter
        components:
          - role: counter
            device: dev-counter
            channel: "1"

Here, a single *pipeline* called ``pip-counter`` is defined. It contains the one available channel of the ``dev-counter`` device (highlighted on line 5) which was shown further above. This component is assigned the ``role`` of ``"counter"`` in this pipeline. For multi-channel devices, it is also possible to define a pipeline for each channel automatically, e.g. using the following definition:

.. code-block:: yaml
   :linenos:
   :emphasize-lines: 2,6

    pipelines:
      - name: pip-counter-*
        components:
          - role: counter
            device: dev-counter
            channel: each

Note the ``channel: each`` highlighted on line 6. Here, a set of pipelines would be created using each of the available channels in ``dev-counter``, replacing the ``*`` in the name of the pipeline(s) on line 2 using the channel. Therefore, when coupled with the above devices section, one pipeline would be created, with name ``pip-counter-1``. However, if the ``dev-counter`` were to contain more than one channel, a pipeline would be generated for each channel.

.. tip::
    For example, the devices shown in the :ref:`concepts diagram <concepts>` above could be defined as:

    .. code-block:: yaml
        :linenos:

        devices:
          - name: device 1
            driver: "driver 123"
            address: "192.168.1.1"
            channels: ["1", "2", "3"]
            pollrate: 1
          - name: device a
            driver: "driver abc"
            address: "COM1"
            channels: ["100"]
            pollrate: 5
          - name: device b
            driver: "driver abc"
            address: "COM2"
            channels: ["100"]
            pollrate: 5

    The *pipelines* from the same :ref:`concepts diagram <concepts>` can be defined using:

    .. code-block:: yaml
        :linenos:

        pipelines:
          - name: pipeline a1
            components:
              - role: dev 123
                device: device 1
                channel: "1"
              - role: dev abc
                device: device a
                channel: "100"
          - name: pipeline b2
            components:
              - role: dev 123
                device: device 1
                channel: "2"
              - role: dev abc
                device: device b
                channel: "100"
          - name: pipeline 3
            components:
              - role: dev 123
                device: device 1
                channel: "3"

.. note::

    The ``pollrate`` here is an internal setting for **tomato**. It is the frequency with which the *job* interacting with the device driver asks the driver for data, **not** the frequency with which the *driver* asks the hardware for data! This latter "sampling" frequency can be defined in each individual *task* submitted as a payload of a job.


.. _payload-file:

Payload file
````````````
The *payload file* contains all information required to enter a job into the queue and allow its assignment onto a pipeline. The overall schema of the payload is defined in the :mod:`dgbowl_schemas.tomato.payload` module, and is parsed using :func:`dgbowl_schemas.tomato.to_payload`.

Of particular importance here is the specification of the individual tasks within the :obj:`Payload.method <dgbowl_schemas.tomato.payload.Payload.method>` field. These tasks, represented by the :class:`~dgbowl_schemas.tomato.payload.Task` class, are distributed onto individual components of the pipeline, by matching the :obj:`~dgbowl_schemas.tomato.payload.Task.component_role` attribute of the task with the ``component.role`` field of the pipeline, and then executed in sequence. Some general task parameters are abstracted by **tomato**, such as the :obj:`~dgbowl_schemas.tomato.payload.Task.max_duration`, :obj:`~dgbowl_schemas.tomato.payload.Task.sampling_interval` and :obj:`~dgbowl_schemas.tomato.payload.Task.polling_interval` attributes. The other are driver or component specific, and can be specified using the :obj:`~dgbowl_schemas.tomato.payload.Task.task_params` field of the task.

.. admonition:: TODO:

  Currently, **tomato** does not check whether the :obj:`~dgbowl_schemas.tomato.payload.Task.sampling_interval` is realistic. However, such validation is planned for a future release, see https://github.com/dgbowl/tomato/issues/127.


As of ``tomato-2.1``, execution of a certain task can be postponed and triggered to coincide with the start of a different task; for this, the :obj:`~dgbowl_schemas.tomato.payload.Task.start_with_task_name` attribute of the triggered task needs to match the :obj:`~dgbowl_schemas.tomato.payload.Task.task_name` of the triggering task. Similarly, the execution of a task can be stopped once a different task *starts*, by setting :obj:`~dgbowl_schemas.tomato.payload.Task.stop_with_task_name` accordingly.

As of ``tomato-2.0``, the :obj:`~dgbowl_schemas.tomato.payload.Task.task_params` specified for each task in the payload are validated by the device driver. In particular, the values of all entries within :obj:`~dgbowl_schemas.tomato.payload.Task.task_params` are checked for compatibility with the :obj:`Attr.type` and :obj:`Attr.options` (if supplied), as well as against the provided :obj:`Attr.minimum` and :obj:`Attr.maximum`.
